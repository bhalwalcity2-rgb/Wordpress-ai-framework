# ADR-0003: The v2 Content Schema Is Canonical

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-03 |

## Decision

The section-typed content schema introduced for the Henderson location page is the canonical contract for every location and service content file. It is defined by `content-engine/config/schema/location.schema.json` and `service.schema.json`, and enforced by `content-engine/bin/validate-content.py`. The earlier flat schema — a `sections[].body` string — is superseded and rejected by validation.

## Context

Two incompatible schemas were in the repository at once. The renderer was upgraded to the section-typed form (`template-parts/location-written.php` reads `paragraphs[]`, `blocks[]`, `table{}`), but eleven of twelve content files were left in the flat form storing prose under `body`.

Nothing mapped one to the other and nothing detected the mismatch. `rich-content.php` returns early only when the heading is *also* absent, so those pages rendered their `<h2>` and silently dropped every paragraph beneath it. Verified in production: `/service-areas/paradise/` served five long paragraphs — a hero line and four FAQ answers — while `/service-areas/henderson/` served twenty-five. Roughly 1,200 words of written prose existed in the repository and reached no page.

A schema is only a contract if something enforces it. The absence of enforcement is what let the fork persist through several deploys.

## Alternatives Considered

- **Keep both schemas, teach the renderer to accept `body`** — Rejected. Preserves the fork permanently, requires every future section template to handle two shapes, and leaves the underlying defect — content silently not rendering — undetectable.
- **Make the flat schema canonical** — Rejected. It cannot express what the pages already need: sub-blocks, reference tables, images, step and CTA sections, per-section eyebrows. Henderson would have to be demoted to reach it.
- **Migrate the prose while migrating the structure** — Rejected for this decision. Rewriting copy and changing the contract at the same time makes it impossible to tell which change caused a difference in output. Structure is migrated mechanically here; content quality is a separate, later phase.

## Consequences

- Content files declare structure explicitly: `sections[].type` is one of `content`, `steps`, `cta`, `areas`. An unrecognised type is a validation error rather than, as before, silently falling through the renderer's `default:` branch and being drawn as a rich-content section.
- Prose lives in `paragraphs[]`. The `body` key is rejected outright — it is the exact shape that failed silently.
- Business identity is tokenised: content files carry `{business}` and `{phone}`, never literals, so `business-config.php` stays the single source of truth. Enforced by the same validator.
- The eleven flat files were migrated structurally — `body` split on blank lines into `paragraphs[]` — with the prose preserved byte-for-byte. No copy was rewritten under this ADR.
- `internal_links` is retained as a deprecated, optional key. No PHP reads it. It warns rather than fails, so the contract can be frozen without a content sweep; removing it is separate follow-up work.
- Validation runs in CI (`.github/workflows/validate.yml`). A malformed or non-conforming file fails the build instead of quietly degrading a live page to the templated fallback.

Human-facing contract documentation: `docs/architecture/content-schema.md`.
