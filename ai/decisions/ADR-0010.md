# ADR-0010: Written Pages Get the Homepage Layout, and Promotion Stops Silently Removing It

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-14 |
| Amends | ADR-0004 |

## Decision

Two changes, one cause.

1. A new Tier 2 section type, **`highlights`**, renders the homepage's "why choose us" card grid from cards the page writes itself. ADR-0004's rejection of a *config-sourced* `why_choose_us` opt-in stands unchanged.
2. The publish gate **refuses to promote a draft that would remove sections or images from a page that is already live**, unless `--allow-regression` is passed.

## Context

A written page could not look like the homepage, and promotion could quietly make an existing page look worse. These sound like two problems. They produced one symptom: written pages that read as unbroken columns of text.

The layout gap was narrow but real. Of the homepage's components, a written page could already express prose, service cards, steps, CTAs, the areas grid and section photography, and received vehicles, testimonials, the trust strip, contact and the closing CTA globally. Only the `why-choose-us` card grid had no route at all, because ADR-0004 closed it deliberately: its content is generic differentiator copy, and making it one line of JSON to drop in would have made the templated pattern the path of least resistance.

That reasoning was about *content*, not about the component. A card grid whose cards must be written by the page cannot carry identical copy to a dozen pages, because there is no config to pull from — writing four cards is as much work as writing the prose ADR-0004 preferred, and it produces a page that looks like the rest of the site. The objection does not apply, so the component returns under a type that cannot reproduce the failure.

The second problem was a live defect. Promotion writes `draft.content` over the destination file wholesale. Henderson's pre-pilot page carried four section photographs and an `areas` block, added in `469e364`; the 3C-5 draft was authored from evidence and carried neither. Promoting it in `97b6b72` dropped all five components, and the deploy took a text-only Henderson page to production. Every gate check passed, because nothing compared the new page to the old one. The gate recorded `previous_destination_sha256` — it could see the page had changed and never asked what the change cost.

This is the more important half of this ADR. A quality gate that only inspects the artifact in front of it will approve any single artifact that meets the bar while a page silently loses everything that made it good.

## Alternatives Considered

- **Render `why-choose-us` globally on written pages (Tier 1)** — Rejected, again. Identical cards on every page is the templated pattern ADR-0004 named, and a global component cannot be omitted by a page that has nothing distinct to say.
- **Let `highlights` fall back to config when the page omits `cards`** — Rejected. The fallback would be chosen every time, which is precisely the config-sourced opt-in ADR-0004 refused. `cards` is required and has no default.
- **Carry presentation forward automatically at promotion** — Rejected. Merging the old page's images into the new content means promoting something no one wrote and no approval hash covers. The gate names what would be lost and stops; a person decides.
- **Exclude images and Tier 3 blocks from the approval hash so presentation can be fixed without re-approval** — Rejected. Alt text is prose a reader encounters, and an `areas` block changes internal linking. Both belong inside what approval covers.
- **Warn instead of block on regression** — Rejected. The Henderson loss would have produced a warning in a passing run, which is how it went unnoticed in the first place.

## Consequences

- `highlights` requires `heading` and 2–4 `cards`, each with `heading` and `description` and an optional `icon`. No config resolution, no `items`, no fallback.
- On a `service_area_transactional` page (ADR-0009) the cards will largely restate business-wide promises — free towing, a firm offer, payment at pickup — in that page's own framing, because those promises *are* what the page is for. That is expected and is not what the type is guarding against. What it prevents is those cards arriving pre-written from config, identical down to the wording, on every page at once. Differentiation for such a page rests on structure, FAQ and entity checks, not on its cards.
- Section shapes: `common.schema.json`. Dispatch: `template-parts/sections-loop.php`, routed to the existing `sections/why-choose-us.php`.
- `component_regressions()` in `publish-gate.py` compares section-type counts, section-image counts, and FAQ presence. Prose is deliberately not compared — replacing it is what a rewrite is for.
- The check runs before `--check` returns, so a regression surfaces while the draft is still being edited.
- Promotion records `components_removed`, so an intentional removal is legible afterwards rather than inferred from two hashes.
- `validate-content.py` now fails an image slug absent from `scripts/image-manifest.json`. CI fetches images from that manifest, so an unlisted slug is never downloaded and renders as nothing — the same silent-drop failure as an unknown card slug.
- Henderson's photography and `areas` block are restored to its draft. That re-authoring changes the draft hash, so the existing approval stops applying, exactly as ADR-0008 intends.
- A page adopting the homepage's section order becomes structurally more similar to its siblings. The differentiation checks still apply and are the backstop; a page that matches a sibling's shape *and* its vocabulary still fails.

Contract detail: `docs/architecture/content-schema.md`. Gate: `content-engine/bin/publish-gate.py`.
