# ADR-0002: `content-engine/` as a Top-Level Directory

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-03 |

## Decision

Content contracts, validators, and (in later phases) the research and briefing pipeline live in a new top-level `content-engine/` directory, separate from both `scripts/` and the WordPress theme.

## Context

`ai/conventions/folders.md` requires a recorded decision before any new top-level directory is created, and the framework already has two plausible homes for this code. Neither fits.

The content supply chain is not a WordPress concern: it runs before commit, never ships to the server, and must not be deployable. Putting it under `wordpress/` would place non-runtime code inside the FTPS deploy root — `deploy-lvjcb.yml` syncs the whole theme directory, so anything under it reaches production.

`scripts/` is defined by `folders.md` as automation utilities in three fixed subdirectories (`setup/`, `deploy/`, `maintenance/`). The engine is not a utility; it is a pipeline with its own schemas, libraries, and per-page artifacts, and it would need subdirectories that contradict that definition.

## Alternatives Considered

- **`scripts/content-engine/`** — Rejected. Avoids a new top-level directory, but `folders.md` fixes `scripts/`'s three subdirectories and describes its contents as standalone automation utilities. Nesting a multi-part pipeline there misrepresents both.
- **`wordpress/themes/kadence-child-lvjcb/content-engine/`** — Rejected. Ships tooling to production via FTPS and binds a framework-level capability to one project's theme, when the engine is intended to serve every site built from this repository.
- **`ai/content-engine/`** — Rejected. `folders.md` restricts `ai/` to Markdown written for assistant consumption. The engine is executable code.

## Consequences

- `ai/conventions/folders.md` gains a `content-engine/` entry defining its subdirectories and rules.
- The directory is never deployed. `deploy-lvjcb.yml` syncs only the theme directory, so no exclusion rule is needed, and none may be added that would change that.
- The engine is framework-level, not project-level: per-project content stays in each theme's `content/` directory, and the engine is invoked with a theme slug the way `scripts/` utilities already are.
- Engine code introduces no dependency beyond Bash, Python 3 (already required by `scripts/generate-content.sh` and present in CI), and the existing GitHub Actions runner.
