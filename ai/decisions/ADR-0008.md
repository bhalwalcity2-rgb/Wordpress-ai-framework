# ADR-0008: Content Reaches a Theme Only Through the Publish Gate

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-06 |

## Decision

`content-engine/bin/publish-gate.py` is the only sanctioned path into `wordpress/themes/{theme}/content/`. It re-runs every prerequisite at promotion time, requires an approval record naming the exact draft hash, and writes an audit record. CI enforces the rule by requiring every theme content file to trace to a promotion record or to a recorded pre-gate migration allowlist.

## Context

Phase 3C-3 built the brief and the writer, but stopped at `content-engine/drafts/`. Something has to move a draft into the directory the renderer reads, and that step is where every earlier failure in this project would have been caught or waved through.

The failures are worth naming, because each one reached production through a path that looked fine at the time. A phone number belonging to nobody was served on eleven pages. A v1/v2 schema fork silently dropped 3,200 words. A legal claim that Nevada statute contradicts is still live. None of these were malicious; all of them were content changes that nothing was accountable for.

Two things follow. First, the gate cannot trust its inputs: a draft's `status` and a brief's gate verdict are fields in files, and a file is whatever it was last saved as. Second, and less obvious — a gate is worth nothing if the door beside it is open. Nothing prevents editing a content file in an editor and committing it, and schema validation would pass, because the file would be well-formed. It would simply be unaccountable.

Approval needs separating too. Every automated check passing is evidence that content is *not obviously wrong*. It is not a decision to publish, and treating it as one means the first genuinely bad page ships the moment it happens to be well-formed.

## Alternatives Considered

- **Promote automatically when all checks pass** — Rejected. Conflates "no detectable problem" with "someone decided this should be public". The corpus contains a live claim that passes every structural check and is contradicted by statute.
- **Standing per-page approval** — Rejected. Approval would survive the draft being rewritten, which is exactly when it should lapse. Binding approval to the draft hash makes re-authoring re-open the decision.
- **Trust the draft's `status: validated`** — Rejected. That is a self-report. The gate re-derives angle status, claim publishability and structural similarity from the registries.
- **Let the gate deploy as well** — Rejected. Promotion changes the repository; deployment ships it. Merging them would put FTPS credentials behind a content decision and make rollback mean two different things.
- **Require every content file to have a promotion record, with no allowlist** — Rejected. The twelve current files predate the gate by several phases. Pretending they came through it would be false provenance — the specific failure this system exists to prevent — and blocking CI until they are rewritten would stop the repository working to satisfy a formality.

## Consequences

- Promotion re-runs the brief, draft and research validators, plus angle authority, claim provenance, identity tokenisation, coverage, structural differentiation and link resolution. Any failure leaves the draft untouched.
- `content-engine/approvals/{slug}.json` must name `draft_sha256`. An approval for a different hash is refused with the reason.
- Modes are explicit: new refuses to overwrite, `--update` replaces deliberately and records the previous hash, `--dry-run` writes nothing, `--check` stops after prerequisites.
- Promoting a location file for the primary city is refused: the homepage owns that intent (ADR-0004/ADR-0005).
- Slugs are validated and destinations are containment-checked after resolution, so no argument can direct a write outside the theme's content directory.
- The source draft is never modified or deleted. It is the audit counterpart to the record.
- CI gains provenance verification, brief/draft validation, and the gate self-test, inside the reusable workflow deployment already depends on.
- **The allowlist is a stated compromise, not a loophole.** It matches on path, so an allowlisted file can still be hand-edited without detection. Every properly promoted page removes an entry, and the exposure shrinks to nothing.
- Nothing has been promoted. No approved angle exists, so the gate refuses every page — the Phase 3C-3 result, now enforced at a second stage.
