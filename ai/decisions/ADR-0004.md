# ADR-0004: Three-Tier Composition for Written Pages

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-03 |

## Decision

A written page is composed of three tiers, and each candidate component belongs to exactly one: **global verified components** rendered on every written page from `business-config.php`; **content-driven sections** the page declares in its own content file; and **config-sourced sections the page opts into by slug**, where the page chooses placement and subset but never restates the data.

## Context

Giving a page a content file replaced the whole generic layout with the file's own sections. That was correct for prose and wrong for everything else: Henderson lost the vehicles slider and the testimonials the generic location page had shown, and wiring service pages to the same renderer (ADR-0003, Phase 2) extended that loss to four more pages. Social proof disappeared as a side effect of writing better copy.

The naive repair — let a content file declare its own testimonials — is worse. `ai/memory/master-website-workflow.md` Phase 07 forbids fabricating reviews, review counts, or review metadata, and per-page review lists are exactly how that happens. The same argument applies to purchased-vehicle inventory. These are site-wide facts with one owner.

The opposite extreme — render every component globally — reintroduces the problem the content contract exists to solve. A block of identical "why choose us" cards on twelve pages is the templated-page pattern wearing a different hat.

So the question is not *global or content-driven* but *which tier each component belongs to*, decided per component on where its truth lives and whether repeating it across pages is a feature or a defect.

## Alternatives Considered

- **Let content files declare testimonials and vehicles inline** — Rejected. Duplicates business data across a dozen files, guarantees drift from `business-config.php`, and creates the mechanism for fabricated reviews that the master workflow prohibits.
- **Render every generic section globally on written pages** — Rejected. Restores the trust blocks but also restores the identical `why-choose-us` and `what-we-buy` blocks on every page, which is the templating this project is correcting.
- **Make every component opt-in, including testimonials** — Rejected. A page that forgets to opt in silently ships without social proof, which is precisely the failure this ADR is fixing. Trust components must not be omissible by oversight.
- **Add a `why_choose_us` opt-in section** — Rejected, deliberately. Its content is generic differentiator copy that reads the same on every page. Making it one line of JSON to drop in would make the templated pattern the path of least resistance. A written page should say why it is worth choosing in its own prose, in a `content` section.

## Consequences

- **Tier 1 — global, always rendered:** hero, trust strip, recently-purchased vehicles, testimonials, contact information, closing CTA. Sourced from `business-config.php`. Not expressible in a content file, and not omissible by one.
- **Tier 2 — content-driven:** `content`, `steps`, `cta`. The page's own prose, structure, and voice.
- **Tier 3 — opt-in by slug:** `areas` (existing) and `services` (added here). The page chooses whether to include the block, where it sits, which entries appear, and an optional per-entry note; every other field resolves from config at render. A retired service or service area cannot leave a stale card or link.
- Adding a component to Tier 1 changes every written page at once, so it requires a new ADR. Adding a Tier 3 type requires a schema definition, a renderer case, documentation, and validation together — see `docs/architecture/content-schema.md` §7.
- Henderson and the four service pages regain vehicles and testimonials without any content-file change.
- `why_choose_us` remains reachable only through the generic layout. If a written page needs that argument, it writes it.

Contract detail: `docs/architecture/content-schema.md`. Section shapes: `content-engine/config/schema/common.schema.json`.
